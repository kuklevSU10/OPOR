# Правила работы помощника в проекте OPOR

Этот файл - короткий контракт для новой ИИ-сессии. Сначала прочитай его, затем
верхний раздел `HANDOFF.md`.

## Роль проекта

Идет перенос AutoCAD-плагина `opor` с VBA/DVB на чистый AutoLISP. Цель - сохранить
паритет с VBA там, где он уже доказан, и дальше аккуратно делать правки ТЗ Дмитрия.

Главный код: `OPOR/*.lsp` и `OPOR/opor.dcl`.

## Старт каждой новой сессии

1. Прочитай `README.md`.
2. Прочитай этот файл.
3. Прочитай только верхний живой раздел `HANDOFF.md` до первого большого описания
   проекта, если задача не требует глубокой истории.
4. Посмотри текущую структуру папки, но не перемещай и не удаляй файлы без явной
   просьбы пользователя.
5. Если задача про конкретный баг или прогон, сначала прочитай свежие `.log`
   как CP1251.

## Главные правила

- Не ломай доказанный паритет с VBA ради красивого рефакторинга.
- Не переписывай архитектуру без необходимости. Двигайся маленькими проверяемыми
  правками.
- При сомнении "как должно быть" сверяйся с VBA в `12/vba_sources/vba_sources/`.
- Эталонные DWG в `эталоны/` не портить. Рабочие копии держать в `рабочие_прогоны/`.
- Исходники заказчика в `исходник/` считать неприкосновенными, кроме явно оговоренных
  правок DWT/DWG.
- `OPOR/opor.dcl` хранить в CP1251. Не конвертировать молча.
- Логи AutoCAD читать как CP1251. Свежий лог может быть залочен AutoCAD; тогда читать
  shared-read или попросить закрыть чертеж.
- После значимого шага обновлять верхний раздел `HANDOFF.md`: что сделано, что
  проверено, что осталось.

## Кодовый стиль

- Писать в стиле существующих `opor-*` функций.
- Сохранять модульные границы: config/errors/geometry/cleanup/dump/tables/ui/trim/grid/
  supports/levels/dcl/core.
- Новые функции называть `opor-...`.
- Для COM-вызовов использовать защиту `vl-catch-all-apply`, если объект или метод может
  отсутствовать в реальном DWG.
- Для boolean из COM (`:vlax-true`, `:vlax-false`) использовать `equal`, не `=`.
- Не перекрашивать и не менять существующие пользовательские слои, если задача прямо
  не про это.
- Все созданные портом объекты должны быть помечены XData `OPOR`, если это объект,
  который потом должен чиститься через `OPORCLEAN`.

## Проверка

Перед AutoCAD-прогоном полезная локальная статика:

- баланс скобок во всех `OPOR/*.lsp`;
- число `defun`;
- поиск неразрешенных вызовов `(opor-...)` и quoted callbacks `'opor-...`;
- поиск опасных сравнений `= ... :vlax-true`.

После AutoCAD-прогона:

- прочитать свежий лог;
- проверить строки завершения `Const`/`Var`, `AREA`, `ITOG`, `LENGTH`, `LAG`;
- при изменениях сетки сверять `DUMPALL`, `OPORDUMP`, `OPORTABLES`;
- сверять golden-master числа с `эталоны/README.md`.

## Документы статуса

- `README.md` - карта проекта и быстрый старт.
- `AGENTS.md` - этот рабочий регламент.
- `HANDOFF.md` - живой статус, очередь, история решений.
- `OPOR/README.md` - справка именно по модулю порта.
- `OPOR/IMPLEMENTATION_STATUS.md` - краткий технический статус модуля, может отставать
  от `HANDOFF.md`.

Если статусы расходятся, считать главным `HANDOFF.md`, затем свежие логи AutoCAD.

## Тон работы

Пользователь обычно работает рядом в AutoCAD. Не проси его копировать простыни вывода,
если можно прочитать лог с диска. Пиши коротко и по делу: что проверил, что нашел,
что нужно сделать дальше.
